## 13.1 — How does the application tolerate an availability-zone failure?

Production application workers run across two availability zones in the selected region behind managed load balancing. The regional database uses a multi-zone standby. This design tolerates a zone failure but does not provide automatic cross-region failover.

## 13.2 — What is the disaster recovery time objective?

The documented recovery time objective is eight hours for a regional service recovery from backups. It is an internal recovery objective measured in exercises, not a customer-specific guaranteed restoration deadline. Customer integration recovery remains the customer's responsibility.

## 13.3 — What is the disaster recovery point objective?

The recovery point objective is one hour for production case records, using continuous database log shipping and tested restore procedures. Attachment recovery can lag by up to four hours. The one-hour objective must not be represented as zero data loss or applied to every data type.

## 13.4 — How often are backup restores tested?

Reliability performs a sample database and attachment restore every quarter and a full regional recovery exercise annually. Tests check record integrity, application startup and access restrictions. Failed checks produce tracked remediation work before the exercise is closed.

## 13.5 — Are backups replicated outside the customer's selected region?

No. Backup copies remain in a separate cloud account in the selected region. A total regional loss can therefore affect both production and recovery availability; the standard deployment does not provide geographic backup replication.
